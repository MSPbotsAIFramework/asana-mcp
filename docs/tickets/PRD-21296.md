## Product design

### Goals / Non-goals

**Goals (v1):**
- Build the first version of `asana-mcp`, a stateless MCP server that lets any MCP-compatible agent (Claude, ChatGPT, Cursor, etc.) read and make safe, scoped changes to Asana task/project data on behalf of a single MSPbots tenant, using credentials supplied per-request.
- Cover the core task-management loop an agent is most likely to be asked to do: find/inspect tasks, create a task, update a task (status/assignee/due date/notes), comment on a task, browse projects/sections, and tag/untag a task.
- Each action is logged (structured request/response logging per `vendor-mcp-development-sop.md` §6), and credentials are never persisted or logged in clear text — this directly answers "credentials encrypted and every action logged" from the one-line ask: credentials live only in the per-request HTTP header and in-memory context, never written to disk, env, or logs; "every action logged" means every tool call is logged (tool name, tenant-scoped resource ids touched, outcome, no credential value) via the server's structured logging, not a new Asana-side audit feature (Asana's own audit log is an Enterprise-tier feature outside this connector's control — see Open question Q1).

**Non-goals (v1) — deferred, not required by this ticket's one line:**
- Full 1:1 mirror of the Asana API. No portfolios, goals, custom fields CRUD, team/workspace membership management, attachments/file upload, task dependencies, likes/followers, or SCIM/admin endpoints.
- Deleting tasks or projects. Asana's delete endpoints are destructive and the ticket does not ask for them; SOP §2.7 requires write/delete tools to justify business necessity, and none is stated here.
- Webhooks / real-time push from Asana into MSPbots.
- OAuth2 login flow for end users. The MCP-register API only accepts static header credentials (Current state, above); users authenticate with a Personal Access Token they generate themselves, same pattern as every other MSPbots vendor connector built to date (e.g. `bamboohr-mcp`, `chargebee-mcp`).
- Any change to the Agent Platform UI, the Published Connectors admin page, or the MCP gateway (`mcp-service-gateway`) — this ticket only adds a new vendor behind the existing gateway contract.

### Acceptance criteria AC1..AC10

- **AC1**: Given a valid Asana Personal Access Token is supplied in the connector's credential header, When the agent calls `tools/list`, Then the returned tool catalog includes tools to discover workspaces, search/read tasks, list projects and sections, create and update a task, add a comment to a task, and add/remove a tag on a task (9 tools total, all named `asana_<verb>_<noun>`).
- **AC2**: Given the credential header is missing from a tool call, When any `asana_*` tool is invoked, Then the server returns HTTP 401 before any request reaches Asana, with a body naming the required header.
- **AC3**: Given a valid token, When the agent lists workspaces, projects in a workspace, or sections in a project, Then each list is returned with id and name, respects a `limit` (default 50, hard cap 200), and signals whether more results exist (no unbounded single response).
- **AC4**: Given a valid token, When the agent searches for tasks (by free-text query and/or project/workspace/assignee/completed filters), Then matching tasks are returned with id, name, completed flag, assignee, due date, and a permalink — the agent never needs an internal Asana field name to use this tool.
- **AC5**: Given a valid token, When the agent creates a task (name, project, optional notes/assignee/due date), Then the task is created in Asana and the tool returns its id, name, and permalink.
- **AC6**: Given a valid token, When the agent updates a task's status, assignee, due date, or notes, Then only the fields supplied are changed in Asana, and the updated task is returned.
- **AC7**: Given a valid token, When the agent adds a comment to a task, Then the comment is created as an Asana story on that task and returned with its id and text.
- **AC8**: Given a valid token, When the agent adds or removes a tag on a task, Then the task's tag set in Asana reflects the change and the updated tag list is returned.
- **AC9**: Given Asana returns an error (expired/invalid token, resource not found, validation error, or rate limit), When any tool is called, Then the tool returns the connector's structured error envelope (`{"error": {"code","message","retryable"}}`) instead of a raw exception or 500, with `code` drawn from the SOP's fixed vocabulary (`unauthorized` / `not_found` / `invalid_argument` / `rate_limited` / `upstream_error`).
- **AC10**: Given two concurrent requests carry different tenants' tokens, When both call tools at the same time, Then neither request's token, response data, or any other per-request state is visible to the other (request-level isolation; no shared/global credential state).

## Tech design

### Conclusion

Build `asana-mcp` as a new Python 3.12 + `uv` + FastMCP server, same shape as every other MSPbots vendor connector (SOP §9): Streamable HTTP at `POST /mcp`, `GET /health`, fully stateless, credentials read once per request from a single custom header (`X-Asana-Access-Token`) and never persisted. The only external dependency is Asana's REST API v1.0 (`https://app.asana.com/api/1.0`), called with a plain `Authorization: Bearer <token>` using the user-supplied Personal Access Token — no OAuth flow, because the MCP vendor-register API this connector is onboarded through does not support OAuth (Current state, above). Nine capability-oriented tools cover workspace/task/project/section/tag read and the minimal safe write surface (create/update task, comment, tag) described in Product design.

### Where the current implementation lives

There is no implementation yet — `README.md:1-2` is the entire repository (see Current state). There is nothing in this repo to reuse. The pattern to follow is the organization's existing convention for this exact shape of connector (public REST API behind a static API-key header, no OAuth, no stateful resources): e.g. `MSPbotsAIFramework/bamboohr-mcp`, `MSPbotsAIFramework/chargebee-mcp`. This design does not clone or inspect those repos' code (out of scope for a read-only design pass and not necessary — the shape is fully specified by `vendor-mcp-development-sop.md` §§1,3,4,9), but the dev leg should scaffold from the same SOP §9 structure those repos already follow, not invent a new layout.

### Option analysis

| Decision | Options | Chosen | Why |
|---|---|---|---|
| Credential model | OAuth2 (Asana supports it) vs. Personal Access Token via header | PAT via `X-Asana-Access-Token` | The vendor-register API this connector onboards through only supports static header credentials, not OAuth (`vendor-mcp-development/SKILL.md:471`); OAuth would need a human to register it through a separate, unsupported path. PAT is also what every other read/write MSPbots connector of this shape uses. |
| Tool granularity | Mirror Asana's ~40 task/project endpoints 1:1 vs. consolidate into capability-oriented tools | 9 consolidated tools | SOP §2.1 requires tools to be capabilities, not endpoint mirrors, and caps a single service at ≤20 tools. A 1:1 mirror would also multiply the Decisions-made surface (per-endpoint pagination, per-endpoint error shape) for no agent-facing benefit. |
| Pagination | Expose Asana's raw `offset` token name to the agent vs. an opaque `cursor` | Opaque `cursor`, pass-through value | Keeps the tool contract vendor-agnostic and consistent with the platform's general list-tool convention (`limit` + opaque cursor + `has_more`); the value itself is still exactly what Asana returned, so no extra state or decoding logic is introduced. |
| Write scope | Full CRUD (incl. delete) vs. create/update/comment/tag only | No delete tools | SOP §2.7 requires a stated business need for destructive tools; the ticket states none, and dropping delete removes an entire class of "agent accidentally deletes a task" failure mode for a v1 connector with no test account to rehearse recovery against. |

### Data & API contract

Transport: `POST /mcp` (Streamable HTTP, JSON-RPC 2.0, MCP protocol), `GET /health` → `{"status":"ok"}`.

Credential header (single, required for every `asana_*` tool call):

| Header | Required | Type | Meaning |
|---|---|---|---|
| `X-Asana-Access-Token` | yes | password | Asana Personal Access Token, created at `https://app.asana.com/0/my-apps` → "Create new token". No OAuth app registration needed. |

Missing header → HTTP 401, body: `{"error": {"code": "not_configured", "message": "Missing required header: X-Asana-Access-Token", "retryable": false}}`.

Tools (all return a JSON string; `readOnlyHint` / `destructiveHint` / `idempotentHint` set per SOP §2.6; none are marked destructive — no delete tools in v1):

- `asana_list_workspaces() -> {"workspaces": [{"gid","name"}], "has_more": bool, "cursor": str|null}` — read-only. Maps to `GET /workspaces`.
- `asana_search_tasks(workspace_gid?: str, project_gid?: str, query?: str, assignee_gid?: str, completed?: bool, limit: int = 50, cursor?: str) -> {"tasks": [{"gid","name","completed","assignee_gid","due_on","permalink_url"}], "has_more", "cursor"}` — read-only. Maps to `GET /tasks` with the equivalent Asana query filters (`workspace`, `project`, `text`, `assignee`, `completed`, `opt_fields`); at least one of `workspace_gid`/`project_gid` is required (Asana requires a scoping parameter) — missing both → `invalid_argument`.
- `asana_get_task(task_gid: str) -> {"gid","name","notes","completed","assignee_gid","due_on","tags":[{"gid","name"}],"permalink_url"}` — read-only. Maps to `GET /tasks/{task_gid}`.
- `asana_create_task(name: str, workspace_gid?: str, project_gid?: str, notes?: str, assignee_gid?: str, due_on?: str) -> {"gid","name","permalink_url"}` — write, not destructive, not idempotent. Maps to `POST /tasks`; at least one of `workspace_gid`/`project_gid` required, same as search.
- `asana_update_task(task_gid: str, name?: str, notes?: str, completed?: bool, assignee_gid?: str, due_on?: str) -> {"gid","name","completed","assignee_gid","due_on"}` — write, not destructive, idempotent (same input → same resulting state). Only the fields supplied are sent to Asana (`PUT /tasks/{task_gid}` with a partial body — Asana's PUT is already a partial update, matching this tool's "only touch what's supplied" contract with no extra client-side merge logic needed). At least one field besides `task_gid` required.
- `asana_add_comment(task_gid: str, text: str) -> {"gid","text","created_at"}` — write, not destructive, not idempotent. Maps to `POST /tasks/{task_gid}/stories`.
- `asana_list_projects(workspace_gid: str, limit: int = 50, cursor?: str) -> {"projects": [{"gid","name","archived"}], "has_more", "cursor"}` — read-only. Maps to `GET /projects` filtered by `workspace`.
- `asana_list_sections(project_gid: str, limit: int = 50, cursor?: str) -> {"sections": [{"gid","name"}], "has_more", "cursor"}` — read-only. Maps to `GET /projects/{project_gid}/sections`.
- `asana_manage_task_tags(task_gid: str, add?: [str], remove?: [str]) -> {"tags": [{"gid","name"}]}` — write, not destructive, idempotent (adding an already-present tag or removing an absent one is a no-op, not an error). `add`/`remove` accept tag names (resolved to the workspace's existing tags; unknown names create the tag, matching Asana's own `addTag`/`removeTag` semantics) or raw gids. Maps to `POST /tasks/{task_gid}/addTag` and `/removeTag` per item.

Pagination: every list tool takes `limit` (default 50, hard cap 200 — never unbounded) and an opaque `cursor`; the response's `cursor` is Asana's own `next_page.offset` token passed through unmodified, and `has_more` is `next_page != null`. The agent never sees the literal string "offset".

Error envelope (every tool, on any upstream failure): `{"error": {"code": "...", "message": "...", "retryable": bool}}`. Mapping: Asana 401 → `unauthorized` (retryable: false), 404 → `not_found` (false), 400/422 → `invalid_argument` (false), 429 → `rate_limited` (true), 5xx or network failure → `upstream_error` (true).

Backward compatibility: new repo, nothing to be compatible with yet. No DB, no migration, no event/message contract — this connector is stateless and talks only to Asana's API.

### Key flow / sequence

```
Agent -> Gateway: tools/call asana_search_tasks {query:"renew SSL cert"} + tenant's X-Asana-Access-Token (via gateway)
Gateway -> asana-mcp: POST /mcp (forwards header)
asana-mcp middleware: header present -> set ContextVar(token); missing -> 401, stop
asana-mcp tool: reads token from ContextVar -> client.get("/tasks", params={...}, headers={"Authorization": f"Bearer {token}"})
asana-mcp client: on 2xx -> normalize fields, compute has_more/cursor from next_page
                   on 429/5xx -> retry with backoff (bounded) -> still failing -> error envelope
asana-mcp tool -> Gateway -> Agent: JSON string result (or error envelope)
(request ends) -> ContextVar reset in `finally`, nothing cached
```

### Non-functional

- **Idempotency & concurrency**: server is stateless; no shared mutable state across requests. `asana_update_task` and `asana_manage_task_tags` are designed idempotent (re-sending the same call converges to the same end state, doesn't double-apply). `asana_create_task` and `asana_add_comment` are not idempotent by nature (Asana has no client-supplied idempotency key for these endpoints) — calling twice creates two resources; this is the same behavior as calling the Asana UI twice and is not specific to this connector, so no de-duplication logic is added in v1.
- **Performance**: Asana enforces per-token rate limits (confirmed via `developers.asana.com` Rate Limits guide, exact numbers vary by Asana plan/tier and are read from the 429 response, not hardcoded); client honors `Retry-After` and caps total retry time under 120s per SOP §5. List tools default to `limit=50` to keep responses small (token economy, SOP §2.5); `has_more`/`cursor` let the agent page through rather than requesting everything in one call.
- **Security**: credential only ever lives in the request header and the per-request `ContextVar`; never written to env, disk, or logs. `gitleaks detect` run before delivery (SOP §11). No secrets in the repo (placeholders only in README examples).
- **Multi-tenant isolation**: "multi-tenant" here means concurrent MSPbots tenants each supplying their own Asana token on their own request — not Asana's own notion of workspaces. `contextvars.ContextVar`, reset in `finally`, guarantees no token or response data crosses requests (AC10); there is no process-wide cache of any Asana resource.
- **Observability**: structured log line per tool call: tool name, duration, outcome (`ok` / error `code`), and tenant-opaque resource ids touched (e.g. `task_gid`) — never the credential value, never the raw Asana response body.

- **Tool set is 9 capability-oriented tools, not a 1:1 Asana API mirror**, and `custom fields`, `portfolios`, `goals`, `attachments`, `task dependencies`, `likes/followers`, `webhooks`, `SCIM/admin` are excluded from v1. Alternative: mirror more of the API surface up front — rejected per SOP §2.1 (tools are capabilities, not endpoint mirrors) and the ≤20-tool cap; none of the excluded areas were named in the ticket.
- **No delete tools in v1** (tasks, projects, tags-as-resources). Alternative: full CRUD — rejected per SOP §2.7 (destructive tools need a stated business need; none given) and because there is no test account to safely rehearse recovery from an agent mistakenly deleting something.
- **Pagination uses an opaque `cursor` that is Asana's raw `offset` token passed through, not re-encoded** — Alternative: build our own opaque cursor encoding — rejected as unnecessary complexity; Asana's token is already opaque to the agent and passing it through verbatim is simpler and has no downside.
- **Workspace/project scoping is required on `asana_search_tasks` and `asana_create_task`** (at least one of `workspace_gid`/`project_gid`) because Asana's own API requires a scoping parameter for these endpoints — this is not a design choice but a pass-through of an upstream constraint, documented here so the dev leg doesn't "fix" it as a bug.

To change any of these, say so in a comment and move the ticket back to 5b - ready for groom.
